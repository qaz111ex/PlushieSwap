# Plushie Swap

把 PEAK 里的 **BingBong 玩偶**替换成 **米菲兔** 或 **自嘲熊**，可随时切换。

## 功能

- **三种形态自由切换**：原版 / 米菲兔 / 自嘲熊，默认 **自嘲熊**（`ZichaoXiong`）
- **完整替换模型**：尺寸、枢轴、朝向都按原版玩偶精确对齐，手拿、放地上、塞背包都正确跟随
- **卡通化处理**（让它不再像一张 3D 打印照片）：
  - **手绘风描边**：完整的反向壳体（inverted hull），**不删任何面**，用逐顶点"墨线宽度"控制哪里不画线；
    线宽以**屏幕像素**为单位恒定，因此远近、镜头角度、分辨率都不影响粗细
  - **奶油白底色**：亮部颜色向 `#FFFAF2` 提纯，得到干净明亮的布偶感
  - **柔和的接触阴影**：只在褶皱和手脚与身体的交界处留下淡阴影，且经过拉普拉斯平滑，不会有块状噪点
- **按体型调整握点**：米菲兔握在腰部、自嘲熊握在身体（避开它巨大的头），
  且握点会随模型缩放一起缩放
- **物品名与图标**：名字随所选玩偶变化，图标同步替换（带抗锯齿的透明背景 + 黑描边）
- **游戏内热切换**：按 `F7` 循环 原版 → 米菲兔 → 自嘲熊，选择自动写入配置文件
- **保留原版语音与全部游戏行为**：不修改任何音频，也不改变任何物品逻辑

## 安装

1. 确保已安装 **BepInEx 5.4.x**（游戏目录下能看到 `BepInEx` 文件夹）
2. 把 **`PlushieSwap.dll`** 放进：
   ```
   <游戏目录>\BepInEx\plugins\
   ```
3. 启动游戏

**只需要这一个文件**——模型、阴影贴图和图标都已压缩内嵌在 DLL 里（12,133,376 字节，约 11.6 MiB）。

DLL 旁边的同名文件优先级更高。想换模型时，把 `.psmesh` / `_shading.png` / `icon_*.png`
放在 DLL 同目录即可覆盖内嵌版本，无需重新编译。文件名见下表：

| --- | --- |
| `miffy.psmesh` | 米菲兔模型 |
| `miffy_shading.png` | 米菲兔的烘焙阴影贴图 |

## 配置

配置文件：`BepInEx\config\com.zhuanban.peak.plushieswap.cfg`

| 选项 | 默认 | 说明 |
| --- | --- | --- |
| `Plushie` | `ZichaoXiong` | 形态：`Vanilla` / `Miffy` / `ZichaoXiong` |
| `Cycle Plush Hotkey` | `F7` | 游戏内循环切换热键（单个按键，不支持组合键） |
| `World Scale` | `1.0` | 手持 / 地上时的模型大小倍率 |
| `Backpack Scale` | `1.0` | 背包中的额外大小倍率 |
| `Hold Height Offset` | `0.0` | 手持时的额外上下微调（叠加在每个模型自带的握持高度之上） |
| `Rename Item` | `true` | 把物品名改成所选玩偶 |
| `Replace Icon` | `true` | 替换背包图标 |
| `Outline Width (pixels)` | `5.0` | 描边线宽（屏幕像素），`0` 关闭描边 |
| `Shader Override` | 空 | 仅当模型颜色显示异常时才需要改 |
| `Verbose Logging` | `false` | 在日志里输出详细诊断信息（着色器选择、描边构建、模型重建等）；关闭时只写警告与错误 |

在游戏内的模组设置里改动会**即时生效**（唯一的例外是 `Shader Override`：材质按变体缓存，
改它需要**重启游戏**）；直接编辑配置文件不会被热重载——需要**重启游戏**才会读到新值。
（`F7` 只是循环切换形态并把当前选择写入配置，它**不会**重新读取配置文件，在文本编辑器里改完 cfg 再按 `F7` 反而会覆盖掉这次编辑。）

> `[Internal] Config Version` 是本模组自己写的版本标记，用来把旧版默认值迁移到新默认值
> （BepInEx 不会自动更新已存在的配置项）。它已标记为隐藏，不会出现在游戏内的模组设置里。

## 卡通风格是怎么做的

卡通感主要来自四件事，这个模组对应做了：

| 要素 | 做法 |
| --- | --- |
| **① 轮廓线**（最关键） | 反向壳体：整个身体外扩一层（**不删面**），正面剔除后只在剪影外缘露出墨线；线宽按屏幕像素恒定 |
| **② 干净明亮的色块** | 亮度 > 0.55 的颜色向奶油白 `#FFFAF2` 提纯（越亮提纯越多），避免灰扑扑的米色 |
| **③ 简洁柔和的明暗** | 点云 AO，只取上半球遮挡量，并做 3 次拉普拉斯平滑 + 幂次曲线，保留接触阴影但不糊 |
| **④ 少量高光** | 材质 `_Smoothness = 0.14`，给布偶一点柔和光泽而不是塑料反光 |

AO 的数值按颜色打包进一张 1 像素高的调色板贴图，顶点 UV 指向自己颜色块内的对应亮度位置，
所以整个模型（含描边）只需要两个材质、两次绘制（本体一次、描边一次）。

### 描边为什么不删面

早期版本把眼睛、嘴巴、腮红和所有朝下的面从壳体里**删掉**，结果留下上千条边界边，
而每条边界边正是墨线断开的地方——这就是"断断续续、粗细不均"的根源。
现在壳体是一个**完整闭合曲面**，改用逐顶点"墨线宽度"（0 = 不画线）：
宽度为 0 的顶点就落在身体表面上，靠正面剔除自然被身体挡住，所以不画线，也不需要删任何几何。
宽度随 .psmesh 一起发布，运行时精确还原后再按屏幕空间重新外扩。

管线里还有一个 `enclosed`（"被别的壳体包住"）遮罩，但**故意不使用**：它会把贴着裙子的手臂尖端
判成"被包住"，从而切断那里的描边（实测这就是剪影描边缺失 22.6% → 5.1% 的来源）。真正会被
其它壳体遮住的面本来也看不见，不需要靠它来省线。

## 模型是怎么对齐的

替换模型直接按游戏内物品局部坐标生成，关键基准都从真实 prefab 实测得到：

| 项目 | 数值 |
| --- | --- |
| 原版玩偶高度 | `0.9635` 单位 |
| 原版占据的 Y 范围 | `[-0.7345, +0.2290]` |
| 原版 XZ 中心（**玩偶本体**，不含双手） | `X = -0.0315`, `Z = +0.0505` |
| 原版锚点中点 | `(-0.0595, -0.1405, -0.0400)`，即 `Hand_L` / `Hand_R` 两个节点位置的中点（这是**原版锚点**的高度，不是模型的握点高度） |
| 原版锚点间距 | X 方向 `0.5990`，3D 距离 `0.6034` |
| 手持朝向 | 物品 `+Z` 是玩家视线方向，所以模型正面朝 `-Z` |
| 生成模型实体高度 | `0.9635`（两个模型都是；含描边壳的合并包围盒是米菲 `0.9726` / 熊 `0.9735`） |

生成管线会自动：

1. **识别模型正面**——用"面积小且位于上半身"的颜色区块定位眼睛/嘴巴/腮红，
   把它转到面向玩家（米菲兔需转 181°、自嘲熊需转 225°，源模型本来是歪的）
2. **对齐尺寸与枢轴**——缩放到原版高度，XZ 对齐原版身体中心，Y 与原版完全一致；
   加上描边后整体再回正一次，保证含描边的外轮廓正好落在原版包围盒内
3. **烘焙 AO**——对每个顶点统计邻域几何在其上半球方向的遮挡量，平滑后打包成调色板贴图
4. **生成描边壳体**——沿法线外扩并标记为 outline 子网格

握持高度按每个模型单独设定（`tools/build_meshes.py` 末尾的 `grip_fraction`）：

| 模型 | 握持点位于模型高度 | 说明 |
| --- | --- | --- |
| 米菲兔 | 22% | 腰部，正好在她张开的手臂下方 |
| 自嘲熊 | 26% | 身体中部，避开占了身高一半以上的头 |

握持时**不写锚点**：物品自己的 `Hand_L` / `Hand_R` 节点从头到尾保持原版数值不动。
游戏每物理帧读取这两个节点来计算手的位置（`CharacterAnimations.ConfigureIK`），
所以模组改为**在持握时偏移模型本身**：`HoldOffsetFor()` 计算 `锚点中点 - 握点中点 × 缩放`，
把模型的腰部送到手的正下方。切回原版时什么也不用还原——原版数据从来就没被改过。

> 已知局限：原版锚点 X 间距是 `0.5990`。米菲的握点间距只有 `0.3860`，两只手会明显停在
> 身体两侧的空中；自嘲熊的握点间距是 `0.5950`，与原版锚点只差 `0.0040`，几乎贴合。
> 曾尝试过对称收拢手的方案，但因游戏自身的挤压动画会直接改写锚点节点，该方案无法稳定工作，
> **已完全移除**。

模型不是挂在物品根节点下，而是挂在 **`item/Holder/PlushieSwap_Visual`**——这是为继承游戏自己的
"压缩"动画：手持时按住主开火键会触发 `Action_AskBingBong` → `squishAnim.SetTrigger("Squish")`，
该动画控制器只驱动 `Holder.localScale` 和两个锚点的 `localPosition`，原版玩偶就是 `Holder` 的子节点，
所以挂在这里就白拿了同样的挤压效果。`Holder` 静止时是单位变换，平时没有任何代价。

## 自定义模型

想换成别的玩偶，只要提供模型并重新生成 `.psmesh` 即可：

```powershell
# 1. 把 .3mf 放进 models\ 目录
# 2. 编辑 tools/build_meshes.py 末尾，追加一次 convert(...) 调用
# 3. 生成模型（自动降面、修朝向、对齐尺寸与枢轴、烘焙 AO）
python tools\build_meshes.py

# 4. 生成图标
python tools\build_icons.py

# 5. 编译并部署（-RebuildAssets 会自动内嵌资源并校验，见下）
pwsh -File build.ps1 -RebuildAssets -Deploy
```

`build.ps1` 会在编译前**校验内嵌资源与 `assets/` 是否一致**，不一致就直接报错中止——
这堵住了本项目历史上最坑的一个失败模式：`assets/` 重新生成了但 `src/EmbeddedAssets.g.cs`
没更新，运行时优先读内嵌副本，于是"改了却完全没效果"。

`tools/build_meshes.py` 会自动完成：解析 3MF（含 Bambu 多色 `paint_color`）、
按颜色与连通体拆分子网格、保护小细节不降面、按表面积均一化降面、重建带硬边的平滑法线、
自动识别并修正朝向、按原版轮廓归一化尺寸与枢轴、烘焙环境光遮蔽并打包调色板贴图、
生成完整描边壳体与逐顶点墨线宽度、计算握点。

## 从源码构建

需要 .NET SDK（用于 `dotnet build`）与游戏本体（提供编译参考程序集）。

`libs/` 目录**不在仓库里**（已被 `.gitignore` 忽略），需要自己准备：把下列程序集从
游戏 `PEAK_Data\Managed\` 复制过去——`mscorlib.dll`、`netstandard.dll`、`System.dll`、
`System.Core.dll`、`Assembly-CSharp.dll`、`Zorro.Core.Runtime.dll`、`UnityEngine.dll`、
`UnityEngine.CoreModule.dll`、`UnityEngine.ImageConversionModule.dll`、
`UnityEngine.UI.dll`、`PhotonUnityNetworking.dll`；再从 `BepInEx\core\` 复制
`BepInEx.dll` 与 `0Harmony.dll`。这些就是 `PlushieSwap.csproj` 里 `<Reference>` 的全部
HintPath 目标（`mscorlib` 的 `<Reference>` 可以省略，MSBuild 会从 `libs\` 隐式解析到同一个文件）。

```powershell
pwsh -File build.ps1                  # 校验资源 + 编译 + 打包到 dist\
pwsh -File build.ps1 -Deploy          # 同上，并直接复制进游戏
pwsh -File build.ps1 -RebuildAssets   # 先生成模型/图标/内嵌资源，再编译
```

`build.ps1` 会先跑 `tools/verify_assets.py` 校验源 3MF 与已生成资源是否一致，再跑
`tools/verify_embedded.py` 校验内嵌资源（任一不一致则中止；前者保证改了 `models\*.3mf`
后必须重新生成，后者保证 `assets\` 与内嵌副本同步）。
编译后把 `bin\Release\PlushieSwap.dll` 复制到 `dist\`（或游戏目录），并校验部署后的
DLL 哈希与刚编译的一致，同时写下 `dist\PlushieSwap\buildinfo.txt`（提交哈希、构建时间、
SHA-256 与 DLL 的 InformationalVersion）。资源已内嵌，所以产物只有一个文件。

## 已知说明

- 这是**本地视觉替换**，只对装了本模组的客户端生效；未安装的玩家看到的仍是原版玩偶
- 原版玩偶的悬停高亮描边不会作用于替换模型（替换模型是独立材质）
- 模型由第三方 3MF 源文件二次加工生成，著作权归原作者，详见上文「模型署名与许可」
- 描边是逐帧在 CPU 上重算的（每个实例约 1.5 万个顶点），这是在没有 Unity 编辑器、
  无法编译自定义 shader 的前提下，唯一能做到"屏幕像素恒定宽度"的办法
- 本模组完全不修改游戏的语音和音频，也不改变任何物品的玩法逻辑（它只替换外观、
  名称与图标）
